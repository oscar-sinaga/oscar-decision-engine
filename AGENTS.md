# OSCAR Decision Engine — Agent Instructions

You are helping implement **OSCAR Decision Engine**, an internal enterprise credit-risk decision engine for a multifinance company.

IDX iDecision is a local benchmark and visual reference only. Do not blindly copy its scope, UI, or architecture. OSCAR MVP focuses on **core decisioning**, not a full Digital Lending Platform.

## 2. Final Tech Stack

Use this stack unless explicitly changed by the user.

### Backend

- Framework: **FastAPI `0.139.0`**
- Install package: `fastapi[standard]==0.139.0`
- Python: `>=3.12,<3.15` recommended
- Validation: Pydantic v2
- Database: PostgreSQL
- ORM / migrations: SQLAlchemy 2.x + Alembic
- Tests: pytest + httpx
- Server: ASGI using FastAPI standard tooling / Uvicorn
- API spec: OpenAPI generated by FastAPI

### Frontend

- Framework: SvelteKit latest stable at scaffold time
- Language: TypeScript in strict mode
- Styling: Tailwind CSS latest stable at scaffold time
- Tests: Vitest; Playwright for critical end-to-end flows
- Package versions: use latest stable during scaffold, then commit and respect the lockfile

### Dependency Policy

- Backend must pin `fastapi[standard]==0.139.0`.
- Backend and frontend must use lockfiles.
- Do not leave production dependencies floating.
- Do not silently change major dependency versions.

## 3. Product Goal

Build a configurable, deterministic, auditable, versioned decision engine that supports:

- credit application decisioning,

- score/model integration boundaries,
- reason codes,
- immutable decision trace,

## 5. Engineering Principles

- Do not hardcode credit policy.
- Keep decision-domain logic outside API route handlers and UI components.
- Decision logic must be configurable and versioned.
- Active configuration versions are immutable.
- Every production decision must be reproducible and explainable through an immutable trace.
- Every state-changing action must create a business audit event.
- Simulation must not mutate production applications, decisions, or active configurations.
- Backend authorization is mandatory; frontend visibility is not a security boundary.
- Use safe structured expressions; never use `eval`, `exec`, or unrestricted SQL.
- Keep technical application logs separate from business audit events and decision traces.
- Mask PII and secrets in logs, traces, errors, fixtures, and exports.
- Prefer the simplest modular implementation that satisfies MVP requirements.

## 7. Logging, Trace, and Audit Requirements

### Technical Application Logs

- Use structured logs.
- Generate and propagate a request/correlation ID.
- Include service/module, event name, duration, status, and sanitized identifiers.
- Do not log raw application payloads, NIK, full phone/address, tokens, credentials, documents, or raw bureau/eKYC responses.

### Decision Trace

- Store immutable execution evidence required to reproduce and explain a decision.
- Include exact strategy/rule/model versions, sanitized input snapshot, calculated features, ordered step results, reason codes, fallback/error path, and runtime metadata.

### Business Audit Events

- Keep audit events separate from technical logs.
- Record actor, action, entity, version, timestamp, reason/comment, before/after state, request/correlation ID, and approval context.
- Audit records are append-only from the application perspective and cannot be edited by ordinary users.
