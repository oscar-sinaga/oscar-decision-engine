# 15 — Tech Stack Recommendation

## Final Stack Decision

OSCAR Decision Engine MVP will use:

| Layer | Technology |
|---|---|
| Backend framework | **FastAPI `0.139.0`** |
| Backend install package | `fastapi[standard]==0.139.0` |
| Backend language | Python `>=3.12,<3.15` recommended |
| Data validation | Pydantic v2 |
| Database | PostgreSQL |
| ORM / DB access | SQLAlchemy 2.x + Alembic |
| Async server | FastAPI standard server tooling / Uvicorn |
| Backend testing | pytest + httpx |
| Frontend framework | SvelteKit latest stable at scaffold time |
| UI language | TypeScript |
| CSS | Tailwind CSS latest stable at scaffold time |
| Frontend tooling | Vite through SvelteKit |
| API contract | OpenAPI generated by FastAPI |
| Technical logging | Python standard logging or a structured wrapper; JSON-compatible output |
| Correlation | FastAPI/ASGI middleware + context propagation |
| Git delivery | Local phase commits; no autonomous push/deploy |

## FastAPI Version Policy

FastAPI is pinned for MVP implementation:

```text
fastapi[standard]==0.139.0
```

Reason:

- It is the latest FastAPI release observed during the finalization of this pack.
- FastAPI provides automatic validation, OpenAPI, type-hint based schemas, dependency injection, and strong fit for Python-native credit risk workflows.
- Pinning the exact version prevents silent behavior changes during agentic implementation.

Recommended backend Python constraint:

```text
>=3.12,<3.15
```

FastAPI itself supports a wider Python range, but OSCAR should use a modern Python runtime suitable for enterprise development.

## Why FastAPI for Backend

FastAPI is a strong fit for OSCAR because decision engine APIs need:

- typed request/response schemas,
- automatic validation,
- OpenAPI documentation,
- high developer velocity,
- clean dependency injection,
- straightforward testing,
- Python-native integration with credit risk models and data science workflows.

FastAPI should expose the runtime API and Workbench backend API. The decision runtime should stay framework-independent internally so rule/strategy execution can be tested without HTTP.

## Why SvelteKit + TypeScript for Frontend

SvelteKit is recommended instead of plain Svelte because OSCAR is an internal application with multiple routes/screens:

- dashboard,
- decision history,
- decision trace,
- rule editor,
- strategy builder,
- simulation,
- manual review queue,
- audit log,
- admin/RBAC.

SvelteKit gives routing, loading data, layouts, SSR/SPA options, and Vite-based development. TypeScript is required for API DTOs, form validation, table state, and safe integration with generated OpenAPI types.

## Why Tailwind CSS

Tailwind CSS is suitable for fast internal enterprise UI development:

- dashboard layout,
- dense tables,
- forms,
- panels,
- status badges,
- audit/detail views,
- responsive internal tooling.

For MVP, use Tailwind utilities plus a small internal component layer. Do not over-invest in a custom design system first.

## Backend Module Rules

- Keep business logic outside route handlers.
- Use Pydantic schemas for API payloads.
- Use domain services for decision execution.
- Do not hardcode policy logic into Python conditionals except for engine mechanics.
- Store rules/strategy as data/config.
- Every decision must produce trace and audit log.

## Frontend Module Rules

- Use SvelteKit routes for app screens.
- Use TypeScript for all API DTOs.
- Prefer reusable components for tables, forms, badges, trace panels, and audit panels.
- Keep rule editor simple in MVP.
- Do not build a visual canvas first.
- Build step-based strategy screens first.

## Package Version Policy

- Pin FastAPI exactly to `0.139.0` for this MVP handoff.
- Use latest stable SvelteKit/Tailwind at scaffold time, then commit lockfile.
- Do not depend on floating versions in production.
- Do not use `@latest` inside automated implementation tasks after initial scaffold.

## Observability Implementation Guidance

- Prefer Python standard logging with a small structured logging adapter; `structlog` may be added deliberately if it improves context propagation and testing.
- Add ASGI middleware for request/correlation IDs, timing, and safe error mapping.
- Never log raw request bodies by default.
- Expose Prometheus/OpenTelemetry integration only when required; do not make an observability vendor a domain dependency.
- Keep decision trace/audit persistence in domain/application services, not in generic request logging middleware.

## Git and Autonomous Delivery Guidance

- Use an isolated branch/worktree.
- Commit after coherent vertical slices with applicable quality gates passing.
- Update docs and implementation status in the same commit.
- Never push or deploy autonomously.
