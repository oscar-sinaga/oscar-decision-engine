# 07 — API Contract

## 1. API Principles

- Use versioned endpoints: `/v1/...`.
- Runtime API must support idempotency.
- Production decision and simulation must be clearly separated.
- Every production decision returns `decision_id` and `trace_id`.
- PII in responses should be masked based on permission.
- Every request receives a request ID and correlation ID.
- Return `X-Request-ID` and `X-Correlation-ID` response headers.
- Do not expose stack traces, database details, raw third-party errors, or secrets.


## 1.1 FastAPI Implementation Note

This contract must be implemented in FastAPI `0.139.0` using `fastapi[standard]==0.139.0`. All request/response bodies should use Pydantic v2 models. OpenAPI generated by FastAPI is the source of truth for frontend client typing after MVP endpoints stabilize.

## 10. Logging and Audit Contract

- API middleware generates/propagates request and correlation IDs.
- Structured errors always include a correlation ID.
- State-changing endpoints emit a business audit event after successful transactional persistence.
- Critical operations must not report success when required audit persistence fails.
- Technical logs contain endpoint/operation, outcome, duration, safe error code, and sanitized identifiers only.
- Trace/audit retrieval endpoints require explicit permissions and mask PII by default.
- Sensitive exports are permission-controlled and create audit events.

## 11. As-Built Addendum (Implementation v0.1, 2026-07-04)

The implemented API follows this contract with the following additions and precisions. OpenAPI generated by FastAPI (`/docs`, `/openapi.json`) is the authoritative machine-readable contract.

### Additional endpoints

| Area | Endpoints |
|---|---|
| Auth | `POST /v1/auth/login`, `GET /v1/auth/me` |
| Decisions | `GET /v1/decisions` (history search: `application_id`, `decision`, `product_type`, `channel`, `date_from/to`, pagination) |
| Rules | `GET /v1/rules/{id}`, `POST /v1/rules/{id}/versions`, `PUT .../versions/{vid}` (draft only), `POST .../versions/{vid}/reject`, `POST .../versions/{vid}/retire`, `POST .../versions/{vid}/test` (dry run) |
| Rule sets | `GET/POST /v1/rule-sets`, `PUT /v1/rule-sets/{id}/members` |
| Decision tables / scorecards | `GET/POST /v1/decision-tables`, `/v1/scorecards` + version lifecycle mirroring rules (overlap warnings returned for tables) |
| Reason codes | `GET/POST /v1/reason-codes`, `PATCH /v1/reason-codes/{id}` |
| Strategies | `GET /v1/strategies`, `GET /v1/strategies/{id}`, `PUT .../versions/{vid}`, `POST .../versions/{vid}/reject`, `POST .../versions/{vid}/rollback` (reason mandatory) |
| Simulations | `GET /v1/simulations`, `GET /v1/simulations/{id}` |
| Manual review | `POST /v1/manual-review/cases/{id}/assign`, `/escalate`, `/request-documents` |
| Governance | `GET /v1/approvals` (approval-request queue) |
| Admin | `GET /v1/admin/users`, `GET /v1/admin/roles`, `PUT /v1/admin/users/{username}/roles` |
| Meta | `GET /v1/meta` (feature registry, operators, enums for the workbench) |
| Monitoring | `decision-summary` also returns `decision_counts`, `error_rate`, `manual_review_queue_size` |

### Contract precisions

- `POST /v1/decisions` returns **201** with `execution_mode` in the body; validation failures of configured required fields return **422** `VALIDATION_ERROR` with per-field details (no decision row is created; see ADR-006).
- Missing active strategy or unresolvable configuration returns **422** `CONFIGURATION_ERROR`.
- Identifiers are formatted `DEC-YYYYMMDD-XXXXXXXXXX` (also `TRC-`, `CASE-`, `SIM-`, `APR-`).
- Simulation responses use `draft_result` for the *target* version (active version if `strategy_version_id` omitted); `active_result` is null unless `compare_with_active=true` and the target differs from the active version.
- Editing non-draft versions returns **409** `IMMUTABLE_CONFIGURATION`; self-approval returns **403** (maker-checker).
- `GET /v1/decisions/{id}/trace` records a `DECISION_TRACE_VIEWED` audit event.

## 12. Phase 2 Addendum (2026-07-05)

Post-MVP endpoints added in Phase 2:

| Area | Endpoints |
|---|---|
| Feature catalog | `GET/POST /v1/features`, `PATCH /v1/features/{id}` — governed data dictionary that drives rule/strategy validation and `/v1/meta` (`rule.view`/`rule.create`) |

## 13. Phase 3 Addendum (2026-07-11)

### Rule authoring and metadata

- Rule create/version endpoints accept exactly one of: legacy `condition` + `action`, v2 `branches` + optional `default_actions`, or `expression` + `output_target`.
- `GET /v1/rules/{id}` returns normalized definitions, `sql_preview` (display only), and the persisted expression text/compiled definition where applicable.
- `POST /v1/rules/{id}/versions/{version_id}/test` returns matched branch, ordered actions, and `outputs_after` for the generated workbench test form.
- `GET /v1/rules/{id}/usage` reports rule sets and strategy versions using the rule.
- `POST /v1/expressions/validate` parses, resolves, type-checks, and reports safe AST metadata. It requires `rule.author_expression`; it never executes SQL.
- `GET /v1/meta` additionally returns `operators_by_type`, `writable_outputs`, `node_types`, `rule_kinds`, and managed `rule_categories`.
- `GET/POST /v1/rule-categories` and `PATCH /v1/rule-categories/{id}` manage audited categories.

### Strategy graph compatibility

Strategy-version create/update accepts exactly one of:

```json
{"steps": [{"order": 1, "type": "RULE_SET", "reference_code": "ELIGIBILITY_MOTOR"}]}
```

or:

```json
{
  "graph": {
    "nodes": [
      {"node_key": "start", "node_type": "START", "position": {"x": 0, "y": 80}},
      {"node_key": "eligibility", "node_type": "RULE_SET", "reference_code": "ELIGIBILITY_MOTOR", "position": {"x": 240, "y": 80}},
      {"node_key": "end", "node_type": "END", "position": {"x": 480, "y": 80}}
    ],
    "edges": [{"from": "start", "to": "eligibility"}, {"from": "eligibility", "to": "end"}]
  }
}
```

Responses always include `graph`; `steps` is also returned only when the graph is a simple linear path. Graph validation is repeated on save, submit, and activate.

### Decision tables

The existing `/v1/decision-tables` version endpoints remain the contract for the grid editor. Version responses include computed `warnings`, including overlapping rows. Outputs support decision, reason code(s), risk grade, approved limit/formula, tenor, and pricing fields. No separate browser-only storage exists.
